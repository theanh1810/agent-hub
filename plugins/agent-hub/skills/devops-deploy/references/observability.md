# Observability — monitoring, alerts, logs

Load when setting up or checking monitoring, alerting, logging or a runbook entry of `SERVER-INFO.md`.

- **Monitoring starts from the on-call's questions**: write 2-4, tie each signal to one. Metrics say *something is wrong*, traces say *where*, logs say *why*.
- **Alert on symptoms** (error rate, p99, queue age), not causes (CPU, disk). Each alert has a clear action, a runbook link and a justified threshold. Two levels only: page now, ticket this week. A new alert is fired once as a test.
- **Metrics, traces and the ship gate**: instrument RED (rate, errors, duration) on every endpoint and external dependency, queues and pools by saturation; read percentiles from histograms, never an average; metric labels come from small fixed sets (route template, status class), never a user id, raw URL or message text, because each label combination is a separate series. Trace across every outbound call with OpenTelemetry auto-instrumentation, manual spans only around meaningful units of work, context propagated over every async boundary. Log levels are used consistently (`error` an invariant broke, `warn` degraded but handled, `info` a business event, `debug` off in production). The ship gate: before a deploy, the dashboards and alerts that answer the on-call questions exist and each new alert was fired once and reached its channel with a working runbook link. Alert numbers (error rate, p99, queue age, dashboard range) are read from group observability of `templates/thresholds/thresholds.yaml`: examples until a project replaces them from its SLO and approves the group (`refs/thresholds.md`). Update the runbook when closing an incident that used it.
- **`SERVER-INFO.md` declares** who owns each alert, the channel it goes to, and a short runbook of at least three lines: what it means, the first query to run, the escalation path.
- **Logs** are structured, with stable event names and a correlation id passed through every outbound call and async boundary; no secret or personal data; latency as a histogram with labels from a small fixed set.
- **Fetched log artifacts** carry the correlation id (request id) and the entry-point name; where several paths share one log stream (schedule, replay, manual run) each must be distinguishable.
- Logs, queries and paths quote only allowed fields; never a whole request or response body or an auth header.
- **Secrets**: a secret reference is not a secret disclosure; a warning is a finding only when a less-trusted reader, output, log or artifact exposes the value.
- **Exposure claims**: never infer live exposure from a config file alone; name the environment using it, the override layer that changes it, and whether the code path runs. Separate "confirmed in the repo" from "needs observing on the host".
