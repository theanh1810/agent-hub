# Browser flow

1. **Setup**: fixtures from `task_definition.fixtures`; seed per the plan; capture baselines if `visual_regression.baselines` is defined; clear the network and console buffers. Pick elements and wait for pages as `refs/roles/test/browser-lifecycle.md § Finding things on a page` says.
2. **Per flow**: init `flow_context: { flow_id, current_step, state, results, api_observations: [], ui_api_links: [] }`; run setup → steps → teardown; keep it across the scenarios of the flow, never lose it between them. An element not found is not a fail until re-snapshotted.
3. **Wait strategies**: `network_idle` | `element_visible:selector` | `element_hidden:selector` | `url_contains:fragment` | `dom_content_loaded` | `load`. Always wait for a condition, never a guessed time.
4. **Per step**:
   - Pre-action snapshot (L1 baseline), scoped with `target` (and `depth` when deep) to the region the step acts on (`refs/roles/test/browser-lifecycle.md` § Keeping output small), read inline (no `filename`); on a scoped action step, also an unscoped pre-snapshot written to `step-NN-pre-snapshot.txt` just before acting, read only when the effect rule's fallback fires. Then read `browser_network_requests` with the step's `filter`: the highest number it shows is the mark (0 when it shows none).
   - **Actionability gate** for an action step (click, tap, press, select, check, fill, submit): the target resolves to exactly one element and is not disabled (`disabled` or `aria-disabled`). A click error naming `strict mode violation`, `element is not enabled` or `intercepts pointer events` is the same failure. Fail the step `wrong_target` (`not_unique`, `disabled` or `covered`) at stage `1_ui`, no retry; a timeout naming one of these reasons is this failure (the hung rule of `refs/roles/test/resume.md` covers only a timeout with no actionability reason). A step whose text starts `[no-effect] ` (`refs/roles/planner/test-cases.md` § Fields on a case) skips the disabled and covered part; uniqueness still applies.
   - Action, then the wait condition, then the post-action snapshot over the same `target`; on a scoped action step, also an unscoped post-snapshot written to `step-NN-post-snapshot.txt` right after it, read only when the effect rule's fallback fires; when the action removed that `target` and it no longer resolves, take the post-action snapshot unscoped instead of failing the step.
   - Pull `browser_network_requests` → `api_observations[]` (L3): the new requests are those numbered above the mark (the numbers run per tab and a new tab starts at 1, so read a new tab after `browser_tabs` `select`); log the errors and warnings in the console ranges given to the step (every response's link, `refs/roles/test/browser-lifecycle.md` § Keeping output small), never by comparing message text with an earlier reading. At the end of each case, write both with `all: true` (both tools otherwise return only what followed the last navigation), no `filter` and an absolute `filename` into `.cm-tmp/{task_id}/` as `network-{test_case_id}.json` and `console-{test_case_id}.txt` (on `File access denied`, the fallback of `refs/roles/test/browser-lifecycle.md` § Keeping output small).
   - Assert the UI shows the expected response field → `ui_api_links[]` row (L4).
   - **Effect rule** for an action step: at least one of — post-snapshot differs from pre, a request since the mark, the URL changes, a dialog, download or new tab opens, a filled field shows its value. None → fail `no_effect` at stage `2_fe_behaviour`. `[no-effect] ` steps are exempt. How two trees are compared, and the unscoped comparison before this fails, is `refs/roles/test/browser-lifecycle.md` § Keeping output small.
   - Record either failure in `flow_results[].failed_stage` and `stages{}` (no new key) and as the first line of the failure doc: `symptom: wrong_target (<reason>)` or `symptom: no_effect`. Both read snapshots and events already taken.
5. **Per-page final checks**: full, unscoped accessibility tree via `browser_snapshot` (never `target`- or `depth`-limited), a preliminary check of names, labels, headings and alt text: it checks no contrast and gives no score, so the a11y ≥90 threshold is met only by Lighthouse (`categories.accessibility.score` ≥ 0.9) and is otherwise 'not measured' (`skills/testing-e2e/references/checks.md` § Self-critique); an axe-core run the project already has is reported as its violation count, never as meeting that threshold; network status ≥400, read without `filter`, flagged expected or unexpected against `task_definition.expected_4xx[]`; navigation timing via `browser_evaluate` on `performance.getEntriesByType('navigation')` and CLS from a `layout-shift` observer; LCP from Lighthouse (`audits['largest-contentful-paint'].numericValue`); INP comes from neither these calls nor `npx lighthouse <url>` (navigation mode), so it is written 'not measured', as is LCP without Lighthouse; Lighthouse only when a score is needed.
6. **Navigation**: move between pages by clicking the menu; a hard `browser_navigate` drops the socket session.
7. **Locators and warnings**: locate by role first, then label, testID as fallback, CSS last (addy testing-patterns.md:125-222). Console warnings are triaged and reported as findings, never a fail gate (addy browser-testing SKILL.md:236-258).
